# ADR-001 · 星卜 Astroscry 总体架构

**状态**：已接受（2026-10-14）　**阶段**：设计→开发　**决策人**：用户 + 本地检查

## 决策问题

四类术数（西占/塔罗/八字/紫微）在网页端如何架构，才能不用 AI 大模型、成本最低、且未来可扩展？

## 决策

**纯静态单页站点**（无构建、无后端）：原生 HTML/CSS/ES Modules + 4 个 vendor 计算库（lunar-javascript、iztro、astronomy-engine、AstroChart），解读引擎=「core 纯函数计算 → 规则映射 → JSON 语料拼装」。部署=任意静态托管。

## 背景与力量（Forces）

| 力量 | 影响 |
|---|---|
| 禁用 AI 大模型 | 解读必须来自确定性规则+语料，天然不需要服务端推理 |
| 隐私 | 生日数据敏感，本地计算是最强答案，同时消灭后端/数据库/账号三类成本 |
| 术数计算精度取决于成熟历表/排盘库 | 自研历法不可行；许可（MIT/公版）约束了选型空间 |
| 用户无运维 | 纯静态 = 零运维；任何目录托管即可 |

## 被拒备选

| 方案 | 拒绝原因 |
|---|---|
| B. React/Vite SPA | 引入构建链与框架运行时，四库均有 UMD 直用形态，SPA 收益（状态复杂度）在本项目不存在；迁移到 SPA 成本低（core 层无 DOM 依赖），属可逆门 |
| C. Next.js 全栈（SSR+API） | 无服务端计算需求；反而把生日数据送上服务器，破坏隐私不变量；运维成本最高 |
| D. 自研历法/排盘算法 | 农历置闰、节气定气、紫微安星规则的工程复杂度远超本项目价值；已存在 MIT 成熟库 |

## 系统图（数据流 / 信任边界 / 依赖方向）

```
用户 ──表单──▶ pages 胶水层 ──▶ core 纯计算层 ──▶ vendor 四库（信任边界：MIT、本地、无网络）
                                   │
                                   ▼
                             data/interpret-*.json 语料（只读）
                                   │
                                   ▼
                              ui 渲染层 ──▶ DOM
```

- 依赖方向：pages → core → vendor；ui → core 输出（类型约定）；core 不 import ui/pages。
- 信任边界：vendor 库为唯一外部代码；全部本地打包，无运行时网络。

## 后果

**正**：零运维零成本；隐私强保证；许可干净可商用；四库隔离在 core 内，任一库可替换。
**负**：解读文案质量依赖语料整理投入（上限低于 LLM 生成）；无构建 = 手动管理 vendor 与模块加载顺序；体积 ~1MB 静态资源。

## 可逆性

- 库替换：core 适配层隔离，单库替换成本 ≈ 一天级（可逆）。
- 静态→SPA/SSR：core 无 DOM 依赖，迁移为渐进增强（可逆）。
- 重新考虑的触发点：需要服务端共享排盘（如合盘存储、账号系统）→ 引入轻后端，届时重开 ADR。

## 责任

单人项目：用户运行 `node --test tests/` 与浏览器走查；`ponytail:` 注释记录所有已知上限（真太阳时均时差、整宫制、城市表精度）。

## 风险登记

| 风险 | 可能性 | 影响 | 缓解 |
|---|---|---|---|
| 子时/跨日边界排盘争议 | 中 | 中 | lunar 节气定月 + 明示「晚子时归本日」策略；免责声明 |
| 塔罗图片源不可达 | 中 | 低 | v1 纯排版卡面可用，图片为增强项 |
| 解读语料覆盖不足 | 高 | 中 | 分级标注出处；先覆盖高频特征（主星/日主级），组合特征后续补 |
| vendor 库停止维护 | 低 | 中 | core 隔离 + 测试向量在手，替换路径明确 |
