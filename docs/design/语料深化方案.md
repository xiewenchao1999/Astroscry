## 二、决策与兼容性（数据契约视角）

| `interpret-bazi.json` | `bazi-page.mjs`、`bazi-analysis.mjs`（`shiShenDetail/geju/relations/chenggu/spouse/synastry`） | 新增 `analyzeShensha` |

| `interpret-tarot.json` | `tarot-page.mjs`（`topicLens/synthesis/…`） | 新增 `cardDomains`（牌×域） |

**兼容性规则（本次全部为「纯增量」）**：

- 新增键一律**不重命名、不改语义**；既有键（`trait`/`advice`/`planetInHouseTpl`/`aspectTpl`/`shensha.note`/`majorStars`）**原样保留**。
- 消费侧一律**新键优先、旧键兜底**：新条目不命中时回落到原有模板/文案。这样语料与代码可独立演进，任一页在任何缺口下都不会渲染出 `undefined`（这是本项目已两次踩过的坑）。
- 语义变更按「破坏性」处理：本次 0 处语义变更，故无需迁移。

**验证（消费者侧测试，不是生产者自测）**：

1. `npm test` 每条新增语料都配闭合断言（键数、键序、字段齐备、占位符可闭合）。
2. **覆盖率断言**：行星×宫位 11×12 全覆盖、七主星两两 21 对全覆盖、大阿卡纳 ×4 域全覆盖——**缺口就是测试失败**，而不是靠人眼查。
3. 浏览器回归：六个受影响页面走主流程，并在真实 https 站点抽查。

## 五、风险

| 风险 | 缓解 |
|---|---|
| 神煞流派分歧（如天乙贵人「甲戊庚牛羊」vs「甲戊兼牛羊」） | 只用一套主流口诀，**在关于页与语料 note 里写明口诀原文**，不混派 |
| 132 条行星×宫位释义风格漂移、拼接生硬 | 统一句法：一句「能量在哪发力」+ 一句「要注意什么」；写完用脚本抽查长度与重复率 |
| 手写大 JSON 易错 | 统一走**一次性 Node 脚本注入**（JSON.parse → 赋值 → 2 空格 stringify 重写），脚本用完即删（沿用既有做法） |
| 新文案过长挤压版面 | 新内容一律进 `<details>` 折叠或次级行，不改变卡片主结构 |
