## 二、提示词工程：可直接借鉴的五条

### 2.1 分层：规则集 / 口径 / 访谈 / 用神 / 格局 / 示例 分开写

`Numerologist_skills` 每个体系都是同一套骨架：`SKILL.md`（触发条件 + 工作流 + 输出约束）配 `references/`（`ruleset-mainline.md` 默认规则、`interview.md` 访谈库、`yongshen.md` 取用神顺序、`geju.md` 格局、`examples.md` 示例输出）。

要点：**把「口径」与「判断顺序」固化成可版本化的文档，而不是塞进一句 system prompt**。奇门默认规则集写死为 `mainline-cn-v1`，混用流派视为错误路径。

### 2.2 先声明口径，再做结论

原文（奇门 SKILL.md 输出结构第 2 项「使用规则与默认项」）：必须写明当前规则集、时区是否默认、是否按「现在」起局、有无寄宫/中宫/边界提醒。**同一套盘在不同流派下结论不同，不声明口径的解读是不可信的**。

### 2.3 七段式输出骨架（比我们现在的五步多两段）

```
1 已确认信息 → 2 使用规则与默认项 → 3 盘面摘要 → 4 用神与关键依据
→ 5 核心判断 → 6 方位/时机/行动建议 → 7 风险提醒与免责声明
```

我们现在的 `readQimen` 是「识局→盘眼→用神→举要→阻隔」——缺 **2 口径声明**、**6 把盘理转成可执行建议**、**7 高风险主题的现实路径提醒**。

### 2.4 输出风格约束（原文摘录，可直接改造为我们的约束）

- 「面向普通求测者，先说人话，再补术语。术语第一次出现时简要解释。」
- 「不展示完整推理链，只展示用户看得懂的关键依据。」
- 「结论要明确，但语气保持平和。」
- 「不用恐吓式语言，不说『必败』『必死』『无救』。」
- 高风险主题（疾病/法律/重大投资/生死）：**必须额外附现实专业路径建议**。
- 结尾固定免责声明。

### 2.5 「复制粘贴」提示词的产品化（外部证据）

- 36Kr《不用 App、不找占星师，年轻人正在用「复制粘贴」算命》：小红书 `#deepseek 算命` 一个话题 **5608 万浏览 / 35.4 万讨论**；用户路径已从「装 App → 找占卜师」变成「找 prompt → 粘进大模型」。
- `Tarotap` 的 10 个 copy-paste 提示词，结构高度一致：**角色设定 → 出生数据（日期/时间/地点/性别/现状）→ 编号提问清单（4-6 条）→ 输出要求**。分主题分文件（本命盘 / 感情 / 事业财富 / 年度运势 / 深度性格 / 双人合盘 / 换跑道时机…）。
- `mingyu`：只调一次 `/prompt`，服务端同时完成排盘并返回**任务书**（盘面数据 + 提问框架）；需要展示盘面时才调 `/calculate`。这个「prompt / data 双出口」拆分值得抄。

## 三、语料设计：字段标准与深度基线

### 3.1 塔罗：行业字段基线（Tarotoo 18 字段）

| 分组 | 字段 |
|---|---|
| 标识 | name / arcana / suit / 数字序号 |
| 神秘学对应 | element / planet / zodiac |
| 牌义 | upright·reversed **keywords** 与 **meanings**（各一套） |
| 语境 | upright·reversed 的 **love / career / mood / spiritual** 四语境解读 |
| 二元 | yes·no 取值 |
| 溯源 | canonical URL |

对照我们现在的 `site/data/tarot.json` 每张牌字段：`id / arcana / suit / num / name / cn / kwUp / kwRev / up / rev`。

**缺口**：①元素·行星·星座对应（我们只有「花色→元素」的表，没有逐牌）②按提问语境的解读（感情/事业/状态/心灵）③是否型问题（yes/no）。

StarTarot 另给出一条工程纪律：**每个字段都能指回页码出处**；数据集显式排除「AI 生成的解读」，只保历史文本 + Golden Dawn 对应关系。Do/Dont：便于审计的做法是「原文 = 来源，对应关系 = 表，解读 = 我们自己写」。

### 3.2 紫微：深度基线（ziwei-doushu）

我们已经有的：十二宫职、十四主星命宫释义、四化、五行局、身宫。**缺**：

| 能力 | 说明 | 我们的现状 |
|---|---|---|
| 格局判定 | 1100+ 行规则库（紫府同宫 / 日月并明 / 七杀朝斗 / 君臣庆会…） | 无（`interpret-ziwei.json` 只有 `emptyPalace` 一句） |
| 十二神煞 | 本命按生年支起、流年按流年支起 | 无 |
| 星曜亮度 7 档 | 庙/旺/得/利/平/不/陷，另留 3 档粗分类降级 | iztro 主星数据里有亮度字段，未在页面呈现 |
| 运限（大限/流年） | 独立页面级展示 | 引擎有 `ziweiHoroscope`，但只在首页「今日综合」用了一次 |
| 真太阳时（含均时差） | 按经度 + 均时差校正 | 八字页有（仅经度），紫微页无 |
| 古籍原文 | 骨髓赋 / 全集 / 全书 | 无（且该仓古籍为 CC BY-NC-SA，不可原样搬） |

### 3.3 八字：我们已接近基线

已有：强弱量化、月令取格、合冲刑害、称骨、十神详解（kin/topic/text）、四柱宫位、姻缘视角、合婚、神煞键。相较 `mingyu` 宣称的「大运流年**流月流日**细盘」，我们的「大运」只有八步粗粒度——**流年/流月细盘是明确的加深方向**。

### 3.4 西占：缺「图形/配置」层

`Asteria` 与 `AstroChart` 的对照说明：用户预期看到的是 本命盘 + 相位释义 + 元素/三态分布 + 行运叠加。我们有前三者（`natal-reading.mjs`：行星落宫主题 + 相位判词 + 元素/三态主导 + 姻缘）。

**缺**：相位**图形**识别（大三角 / T 三角 / 群星 / 对分轴 / 大十字）——`astro.mjs` 的 `calcAspects` 只出逐对相位，没有组合图形判词。图形是「一眼看懂这张盘」的最高信息密度产物。

## 四、产品设计启示

1. **两个出口，不是一个**：`mingyu` 的 `/prompt` 与 `/calculate` 分离，本质是「给 AI 用的」与「给人看的」两条路。我们的现状只有后者 + 一个需要自供 key 的高门槛入口。
2. **门槛即流失**：「自填端点 + 模型 + 密钥 + 勾选开启」四步，对只想「看看准不准」的访客是硬门槛。而「复制提示词」零门槛、零外联、零成本。
3. **交互式星盘**：AstroChart 给 zodiac/house/planet 挂 click handler；我们自绘的 wheel 目前是静态图（详见改造方案）。
4. **发现性**：`taibu`/`mingyu` 的能力清单本身构成卖点（一览表式「支持能力」）。我们的 `about.html` 有一张来源表，但没有「本站能做什么」的能力总览。
5. **溯源与可信**：`ziwei-doushu` 每条倪师原话带出处时间戳、可跳回视频；StarTarot 每字段带页码。**「可点回出处」是术数类产品建立信任的低成本手段**——我们的 `about.html` 已有来源表，可以把「口径」也做成可展开的出处卡片。

## 六、许可与合规注意（本仓已公开部署，须比自用更严格）

- `Renhuai123/ziwei-doushu` 的**古籍原文为 CC BY-NC-SA 4.0（禁止商用）**，其 518,400 样本数据集为 CC BY 4.0（**须署名**）。本仓公开部署 → **不原样搬运古籍文本与样本数据**；格局「概念名称」属公版术语，可自行撰写判词。
- `StarTarot` 数据集为 CC BY 4.0（署名即用）；其**历史牌义原文本身属公有领域**（Waite 1911 / Equinox 1912）。我们已在 `about.html` 注明塔罗牌义源自 Waite 公版，符合要求。
- `Tarotoo` 的解读文本是**其自行创作的专有内容**（不是公版），**不可复制**；只能抄它的「字段设计」这一层抽象。
- `Numerologist_skills`、`Horosa`、`Brhiza/mingyu` 均为 AGPL-3.0：**不可复制代码入本仓**。本文件只提取其「方法论与结构」写进自己的规范，属思想借鉴，不涉代码分发。
- 结论：**可以抄「结构 / 字段设计 / 提示词骨架 / 交互模式」；不可以抄「文本 / 代码」**。所有新语料由本项目自行撰写。
