# 二期开源调研摘要（00 / 汇总：许清楚 · 2026-10-15）

> 汇总自：`round2/western/开源项目调研-西方-二期.md`（research-west）与 `round2/eastern/开源项目调研-东方-二期.md`（research-east）。
> 所有条目数均经 node 实际解析核验（方法见下），与调研员汇报不一致处已如实标注。

## 一、调研范围与方法

- 范围：西方神秘学（星座/星象/占星/塔罗）+ 东方传统玄学（八字/奇门/周易/求签/掷圣杯），共 21 个开源项目/实现（西 11 + 东 10）+ 8 个语料/规则文件。
- 方法：GitHub Search/Contents API 提取源码与数据 → 落盘语料 → node 脚本逐文件验证可解析性与条目数 → 两路结论交叉比对。
- 数据核验结果：5 个 JSON 全部可解析；观音签分项解 1478 条与汇报一致；**iching-64.json 实际 lines 总数 384 条 + 乾/坤 2 条 special（用九/用六）= 386 爻辞**，与汇报口径一致但需知 lines 数组本身是 384。

## 二、核心结论：可借鉴实现方案 Top 8

1. **「键名即规则」组合解读 JSON**（来源：Astrologer-API active_aspects / RoxyAPI summary.byType，corpus 已给范本）
   结构键承载语义、文本按键查：引擎把盘面归并为键序列（如 `sun-moon-tension`、`wands-dominant`、`major-high`）再查表拼接。是组合解读引擎的最佳形态。
   落点：natal/synastry 模块新增组合判词层；corpus 的 `planetPairs`（20 组已备）直接并入 interpret-synastry.json；塔罗侧同思路建 `cardPairs`。
2. **朱熹《易学启蒙》变爻解卦规则全表**（来源：chengjun/iching）
   0-6 爻动的取辞规则完整（0 动→本卦卦辞；2 动→上爻为主；4 动→变卦下爻为主；6 动→乾坤用九用六…），纯查表、零歧义，天然适配确定性引擎。
   落点：新模块 `core/iching.mjs` 的解卦核心，直接实现为查表函数。
3. **起卦三法（纯函数化）**（来源：bazi-master / chengjun / Johnson-Jia）
   梅花时间卦（年支+月+日 mod 8 上卦、加时辰 mod 8 下卦、总和 mod 6 动爻）、梅花三数法（余 0 归模数值）、铜钱摇卦（3 反=老阴 6…2 反 1 正=少阳 7，老阴老阳为动爻）。注意 bazi-master 时间卦是其自创变体，**不采**，按标准梅花式自实现。
   落点：core/iching.mjs 起卦层；bits（六位二进制、自下而上）作主键检索 iching-64.json。
4. **每日运势生成纪律四条 + transit 权重表**（来源：LeoYeAI/openclaw-master-skills、buda-ai/bunny-agent）
   可推导（每句回溯真实天象）、非宿命论措辞、五维评分总和 14-19、同日 12 座互斥；权重 月★★★★★>日★★★★>快行星★★★>大相位★★。astronomy-engine 全部因子可算，只差文案层。
   落点：horoscope 页文案引擎升级，规则写进 core，句式取 corpus/horoscope-writing-patterns.md。
5. **Waite 1911 塔罗原文词表**（来源：ekelen/tarot-api，已落盘 78 牌）
   含人物牌（侍从/骑士/王后/国王）传统人物侧写与「另一读法」多解，比现有 tarot.json 单句现代中文更适合做组合规则取词根。
   落点：tarot 页深度解读 + 未来 cardPairs 的词根来源；中文对照可直接进 interpret-tarot.json 扩展。
6. **数据驱动牌阵 + 逆位概率可调**（来源：MarketingPipeline/Tarot.js、lawreka/ascii-tarot→Jondi fork）
   牌阵最小结构 `{positions[], description}`，deck 与 spread 解耦（印证现有 tarot-spreads.json 方向）；`reversedRate` 参数使正逆比例按风格可调而非固定 50/50。
   落点：tarot.mjs 抽牌层加 reversedRate 参数（默认 0.5）；新牌阵按最小结构定义。
7. **可配置激活集合**（来源：kerykeion active_points/active_aspects）
   行星集/相位集不硬编码，作为配置面暴露。一期 astro.mjs 是硬编码行星集，这是明确的改造点。
   落点：astro.mjs 行星/相位激活集合配置化（可放 data/ 或模块内常量表）。
8. **六爻纳甲「机械层+推理层」分层蓝本**（来源：Johnson-Jia/liuyao-divination，11 册规则文档已整录进 bazi-qimen-copy-supplement.md）
   装卦纳甲/用神取用/旺衰/动静/断卦八步全文档化，机械层程序算 + 推理层文案，与本项目 core/interpret 分层完全同构。
   落点：二期次阶段扩展（约一周级工作量），先周易后六爻；蓝本文件直接作实现依据。

## 六、风险与注意事项

1. **版权**：guanyin-signs-100.json 来源仓库声明「仅供个人学习与文化研究」；iching-64.json 的白话部分源自 AIzenHi（MIT 但白话为翻译产物）。本地自用无碍，**对外发布前建议白话类文案润色改写**，文件头来源注记保留。
2. **版本标注**：观音一百签各地庙宇版本有差异，语料取浅草寺体系（iowi 版），页面应标注版本来源。
3. **不采项**：bazi-master 时间卦是其自创变体（不采，按标准梅花式）；爬取式运势 API（aztro 等外呼+停更，违背隐私不变量）；OracleLang（AGPL+AI 路线相悖）；Placidus 仅留公式表参考（v1 整宫制不变）。
4. **网络约束**：raw.githubusercontent.com 与 jsDelivr 在本机不可达，后续采集走 api.github.com contents API（未认证限流 60 次/时）。
5. **语料键缺省**：观音签 interpret 按签给键非全键（16 类），渲染必须容忍缺键；iching 特殊爻辞在 special 字段不在 lines 数组，解卦引擎需同时查两处。

## 七、给阶段二（项目评估）的输入要点

1. astro.mjs 行星集/相位集当前硬编码在哪些位置？配置化改动的波及面有多大？

4. 新增 core/iching.mjs 与 pages/iching-page 的目录/命名是否符合 CLAUDE.md 约定（纯计算无 DOM、长文案进 data）？
5. site/data 新增 iching.json、guanyin-signs.json 的文件体积（86/100 条全量文本）对 GitHub Pages 加载的影响，是否需要按页懒加载？
6. tests/ 回归与 no-network 测试是否覆盖新模块（core/iching 不得 import ai-reading；默认零外部请求不变量）？
7. interpret-qimen.json 与 AIzenHi 口径的印证结论是否要在评估报告中落为 ADR（防后续漂移）？
8. 版权策略：白话类语料（iching 白话、观音签）对外发布前的润色改写工作量与范围界定。
